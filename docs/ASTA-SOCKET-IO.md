# Diretta asta sul server Windows

Il server Node.js monta Socket.IO 4.8.4 sullo stesso listener HTTP dell'app. Il percorso `/socket.io/` passa dal reverse proxy Caddy e dalla stessa porta HTTPS 443; nessuna nuova porta sul router. Il client viene servito localmente dal pacchetto Socket.IO, senza CDN.

La sessione `sid` HttpOnly e l'appartenenza alla lega vengono controllate prima di ammettere una connessione. Il client indica soltanto la lega; username e ruolo arrivano dal server. Origini estranee, account amministrativi di sistema e sessioni scadute sono respinti. La verifica della sessione viene ripetuta ogni minuto. Una modifica del gioco resta una richiesta HTTP autenticata: il canale socket non accetta comandi d'acquisto o rilancio.

`persistAuction` emette PostgreSQL NOTIFY nella transazione. L'ascoltatore del server riceve l'evento solo dopo il COMMIT, legge uno stato condiviso e crea in memoria la vista di ciascun partecipante. Non effettua una lettura completa per ogni client o secondo. Le rose avversarie e le statistiche pesanti non vengono ripetute nei messaggi. Tutti ricevono versione, offerta, lotto e scadenza dallo stesso stato. Il client scarta versioni precedenti e conferma l'applicazione della nuova versione. I log `AUCTION_PUSH` e `AUCTION_SYNC_CONFIRMED` riportano lega, versione e numero di dispositivi, senza cookie, indirizzi email o credenziali.

I timer sono impostati sul server in base alla scadenza effettiva e continuano senza client collegati. Socket.IO invia anche avanzamenti, aggiudicazioni e chiusure. All'avvio del servizio vengono ripresi gli orari delle aste attive/programmate. Il client corregge il proprio orologio con un riscontro del tempo server e una stima della latenza. Le reti introducono comunque un ritardo variabile: non si può promettere ricezione nello stesso millisecondo su tutti i telefoni.

Con Socket.IO funzionante, i controlli periodici non interrogano l'API dell'asta. Se manca il canale si riprende il controllo HTTP ogni secondo, senza sovrapporre richieste e con timeout di cinque secondi. Alla riconnessione arriva lo stato attuale completo. Nella sala compaiono «Diretta Socket.IO · sincronizzata» oppure lo stato di recupero. La PWA in background può essere sospesa dal sistema operativo: per avvisare gli utenti offline resta il Web Push, previo consenso del dispositivo.

I tempi sono 60 secondi per chiamare, 60 per la prima offerta e 30 dopo un rilancio. Gli ultimi secondi non sono rallentati; resta l'aggiudicazione anticipata quando tutti gli altri partecipanti hanno passato. `scripts/update-auction-timings.mjs` mostra il piano senza scrivere; `--apply` salva un backup di regole e aste e applica soltanto i valori diversi. Una seconda esecuzione non prolunga di nuovo i timer. Nessuna modifica a voti, risultati, rose o crediti.

Verifiche: test di stanze/sessioni/origini, push dopo commit, riscontro di tutti i peer, riconnessione, avanzamento senza client, sei sessioni con identico lotto/prezzo/scadenza e compensazione dell'orologio. Per la verifica grafica isolata usare `node scripts/preview-auction-socket.mjs`: solo dati sintetici, nessun file .env, calendario o account reale.
